# 개발 문서 양식

- 유형: 3. 개발 문서
- 출력: 페이지
- 제목 수준: 섹션 `#`, 모듈·하위 항목 `###`
- 용도: 시스템·소프트웨어의 설계, 구현, 사용법, 트러블슈팅 기록. 문서 종류에 따라 필요한 섹션만 쓴다. 할 일 분류의 "시스템 설계 내용 정리"는 할 일에 딸린 정리이고, 이 양식은 계속 고쳐 쓰는 독립 문서다(변경 이력 포함).

## ① 노션 DB 속성

| 속성 | 종류 | 선택지 / 비고 |
|---|---|---|
| 문서 제목 | 제목 | 예: 대상 시스템 + 무엇에 대한 문서인지 짧게 |
| 대상 시스템 | 다중 선택 | 문서가 다루는 시스템. 시험일지의 "시험 대상 시스템"과 같은 이름을 쓰면 찾기 쉽다 |
| 문서 종류 | 선택 | 설계 / 구현 / 사용법 / 트러블슈팅 |
| 작성자 | 사람 | 노션에서 직접 선택. 출력에는 이름만 적는다 |
| 상태 | 선택 | 작성 중 / 검토 / 완료 |
| 관련 과제 | 선택 | 과제명 |

## ② 질문 목록

질문 모드에서는 단계 순서대로 한 번에 2~4개씩 묻는다. 자료 모드에서는 비어 있는 **필수**만 묻는다.
자료 모드(코드, README, 커밋 기록, 오류 로그, 메모 등)에서는 자료를 보고 문서 종류를 추정해 한 줄로 확인만 받는다.

### 1단계: 기본 정보와 문서 종류
- **필수** 문서 제목(또는 무엇에 대한 문서인지 한 줄)
- **필수** 문서 종류: 설계 / 구현 / 사용법 / 트러블슈팅 (질문 도구가 있으면 4개 중 고르기)
- **필수** 대상 시스템
- 선택: 작성자, 상태, 관련 과제

문서 종류에 따라 쓰는 섹션이 다르다.

| 문서 종류 | 쓰는 섹션 (이 순서로) | 그중 필수 섹션 |
|---|---|---|
| 설계 | 개요 / 요구사항 / 시스템 구성 / 상세 설계 및 구현 / 변경 이력 / 참고 자료 | 개요 / 요구사항 / 시스템 구성 / 상세 설계 및 구현 |
| 구현 | 개요 / 시스템 구성 / 상세 설계 및 구현 / 사용 방법 / 이슈 및 해결 / 변경 이력 | 개요 / 시스템 구성 / 상세 설계 및 구현 |
| 사용법 | 개요 / 사용 방법 / 이슈 및 해결 / 참고 자료 | 개요 / 사용 방법 |
| 트러블슈팅 | 개요 / 이슈 및 해결 / 참고 자료 | 개요 / 이슈 및 해결 |

- 2단계부터는 고른 문서 종류가 쓰는 섹션의 단계만 묻는다. 각 단계 제목 옆에 그 섹션을 쓰는 문서 종류를 적어 두었다.
- 단계 안의 **필수**는 그 섹션이 고른 종류의 "필수 섹션"일 때만 필수다. 아니면 선택으로 다룬다(자료 모드에서 묻지 않는다).
- 표에서 빠진 섹션이라도 자료나 답변에 그 내용이 있으면 넣는다(순서는 ③ 그대로). 내용이 없는 선택 섹션은 뺀다.
- 두 종류가 섞인 문서(예: 구현 + 사용법)는 가장 가까운 종류 하나를 속성 값으로 정하고, 두 종류의 섹션을 합쳐 쓴다.

### 2단계: 개요 — 모든 종류
- **필수** 목적: 이 시스템(문서)은 무엇을 위한 것인가?
- 선택: 범위(다루는 것 / 다루지 않는 것), 관련 시스템

### 3단계: 요구사항 — 설계
- **필수** 만족해야 할 요구사항은? (기능, 성능 수치, 제약 — 요구사항마다 한 줄)
- 선택: 요구사항별 근거나 출처

### 4단계: 시스템 구성 — 설계·구현
- **필수** 구성요소와 각각의 역할은?
- 선택: 구성요소별 입력·출력(데이터, 신호, 토픽 이름 등), 구조도 그림이 있는지

### 5단계: 상세 설계 및 구현 — 설계·구현
- **필수** 모듈(또는 기능)별로 어떻게 설계·구현했나?
- 선택: 사용한 알고리즘·주요 파라미터, 코드 위치(파일 경로), 흐름도 같은 그림

### 6단계: 사용 방법 — 구현·사용법
- **필수** 실행 방법은? (명령어 그대로)
- 선택: 필요한 환경(OS, 버전, 하드웨어), 설치 방법, 파라미터(이름 / 기본값 / 설명)

### 7단계: 이슈 및 해결 — 구현·사용법·트러블슈팅
- **필수** 겪은 문제마다 증상, 원인, 해결 방법은? (원인·해결을 아직 모르면 모른다고 답해도 된다)
- 선택: 오류 메시지 원문

### 8단계: 변경 이력 — 설계·구현
- 선택: 날짜별 변경 내용과 작성자는? (처음 쓰는 문서면 작성일·작성자로 "최초 작성" 한 줄을 제안해 확인받는다)

### 9단계: 참고 자료 — 설계·사용법·트러블슈팅
- 선택: 참고한 문서·논문·저장소·링크는?

## ③ 본문 뼈대

- `{ }` 는 채울 자리. 출력에서는 내용으로 바꾸거나 `⚠️ 확인 필요` 로 둔다.
- `%% 반복: … %%` 아래 블록은 개수만큼 반복, `%% 선택: … %%` 아래 블록은 내용이 없으면 통째로 뺀다. 섹션 앞의 `%% 선택: ○○ 문서 %%` 는 ②의 표에서 그 섹션을 쓰는 문서 종류다.
- `%% … %%` 줄 자체는 출력하지 않는다.
- 표 안에는 `%%` 줄을 넣을 수 없다. 표의 `{ }` 행은 항목 수만큼 한 행씩 반복한다.

````markdown
# 개요

- 목적: {이 시스템·문서가 무엇을 위한 것인지}
- 범위: {다루는 것 / 다루지 않는 것}
- 관련 시스템: {연결되거나 데이터를 주고받는 시스템·문서}

%% 선택: 설계 문서 %%
# 요구사항

%% 반복: 요구사항마다 %%
- {요구사항}
    - {조건·수치 / 근거}

%% 선택: 설계·구현 문서 %%
# 시스템 구성

📷 [그림: {시스템 구조도 — 구성요소와 연결} — 노션에서 직접 첨부]

| 구성요소 | 역할 | 입력 | 출력 |
|---|---|---|---|
| {구성요소 이름} | {역할} | {입력: 데이터 / 신호 / 토픽} | {출력: 데이터 / 신호 / 토픽} |

%% 선택: 설계·구현 문서 %%
# 상세 설계 및 구현

%% 반복: 모듈(기능)마다 %%
### {모듈 이름}

- {설계·구현 내용}
    - {세부 설명: 알고리즘 / 주요 파라미터 / 주의점}
- 코드 위치: `{파일 경로}`
- 📷 [그림: {흐름도·상태도 등 무엇을 보여주는지} — 노션에서 직접 첨부]

%% 선택: 구현·사용법 문서 %%
# 사용 방법

%% 선택: 환경 정보가 있을 때 %%
### 환경

- {OS / 언어·라이브러리 버전 / 하드웨어}

%% 선택: 설치 방법이 있을 때 %%
### 설치

```bash
{설치 명령어}
```

### 실행

```bash
{실행 명령어}
```

%% 선택: 파라미터가 있을 때 %%
### 파라미터

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `{파라미터 이름}` | {기본값} | {설명 / 단위 / 범위} |

%% 선택: 구현·사용법·트러블슈팅 문서 %%
# 이슈 및 해결

%% 반복: 이슈마다 %%
- 문제: {증상 / 발생 조건}
    - 원인: {원인}
    - 해결: {해결 방법}

%% 선택: 설계·구현 문서 %%
# 변경 이력

| 날짜 | 변경 내용 | 작성자 |
|---|---|---|
| {날짜} | {변경 내용} | {작성자} |

%% 선택: 설계·사용법·트러블슈팅 문서 %%
# 참고 자료

%% 반복: 자료마다 %%
- [{자료 이름}]({URL})
````

## ④ 작성 메모

- 명령어, 파일 경로, 토픽·파라미터 이름, 버전, 오류 메시지는 받은 그대로 쓴다(대소문자, 밑줄, 하이픈 포함). 본문 문장 안에서는 인라인 코드(`` ` ``)로 감싼다.
- 코드 블록에는 언어를 꼭 지정한다(`bash`, `python`, `yaml`, `cpp` 등). 언어를 모르면 `text`. 명령어가 여러 개면 실행 순서대로 한 블록에 넣고, 필요하면 `#` 주석으로 단계를 표시한다.
- 명령어와 코드는 사용자가 준 것만 쓴다. 빠진 단계(설치 명령, 옵션 등)를 추측해 채우지 않는다. 비면 코드 블록 안이 아니라 코드 블록 바로 위 줄에 `⚠️ 확인 필요` 를 적는다.
- 파이프(`|`)가 들어간 명령어처럼 `/`로 바꾸면 뜻이 달라지는 값은 표 칸에 넣지 말고 코드 블록으로 뺀다.
- 시스템 구성 표에서 입력·출력을 모르는 칸은 `⚠️ 확인 필요` 로 둔다. 구성요소가 아닌 것(라이브러리, 설정 파일)은 표에 넣지 않고 상세 설계 및 구현에 쓴다.
- 상세 설계 및 구현의 "코드 위치" 줄과 그림 줄은 정보가 있을 때만 쓴다.
- 이슈의 원인이 확실하지 않으면 사용자가 쓴 확신 정도("추정", "의심됨")를 그대로 살린다. 아직 해결하지 못했으면 해결 줄에 그렇다고 쓰고, 임시 조치가 있으면 함께 적는다. 오류 메시지는 고치지 말고 `text` 코드 블록이나 인용 `>` 으로 원문 그대로 옮긴다.
- 변경 이력의 날짜는 받은 그대로 쓴다. 오늘 날짜가 필요하면 `date +%F` 로 확인한다.
- 구조도·흐름도는 붙여넣기로 들어가지 않는다. 자리 표시만 남기고, 출력 뒤에 "노션에서 직접 첨부할 그림" 목록을 따로 보여준다. 사용자가 원하면 구성요소 표를 바탕으로 Mermaid 코드 블록(```` ```mermaid ````)을 그림 자리 아래에 넣을 수 있다(노션에서 다이어그램으로 보임, 2026-11-27 확인). 표에 없는 연결은 지어내지 않는다.
